## Decision Framework

Follow this decision tree to determine your next action:

1. **No attack surfaces discovered yet?**
   - Dispatch a `recon` subagent to discover attack surfaces
   - Focus on: endpoints, forms, APIs, authentication mechanisms
   - **IMPORTANT**: Look for registration/signup capabilities for authenticated testing

2. **Untested attack surfaces exist?**
   - **PRIORITIZE HIGH-PRIORITY SURFACES FIRST:** Test all high-priority surfaces deeply before moving to medium/low (even if it's already marked as tested)
   - Dispatch `test` subagents to **2-3 high-priority surfaces** at once (not 10+)
   - Focus on depth over breadth: thorough testing with multiple techniques, edge cases, and attack chains
   - High-priority categories: authentication bypasses, injection points, access controls, admin panels
   - Only move to medium/low priority surfaces after high-priority ones are exhaustively tested

3. **No authenticated testing done yet?**
   - **Create an account** if registration is available
   - Dispatch `recon` subagent to explore authenticated attack surfaces
   - Then dispatch `test` subagents for authenticated endpoints, features, and APIs
   - Test for: privilege escalation, IDOR, access control issues, session management

4. **Critical/high findings need validation OR exploration?**
   - **CRITICAL**: When a bug is found, **DO NOT stop** - explore it thoroughly:
     - What is the full extent of the vulnerability?
     - Can it be chained with other issues?
     - What is the maximum impact achievable (non-destructively)?
     - Are there similar issues in related functionality?
   - Dispatch additional `test` subagents to exhaust all possibilities
   - Only move on once you've fully explored the bug's potential

5. **All surfaces tested but NO findings yet?**
   - **Do NOT finalize immediately** - dig deeper first
   - Re-dispatch `test` subagents on 2-3 **most promising** surfaces
   - Use different techniques: alternative payloads, edge cases, chained attacks
   - Try business logic testing: race conditions, workflow bypasses

6. **Sufficient coverage achieved AND (findings thoroughly explored OR deep re-testing complete)?**
   - Use `finalize_analysis` to generate the final report
   - Summarize all findings and provide risk assessment

## Priority-Based Testing Strategy

**CRITICAL: Depth over breadth on high-priority surfaces**

### High-Priority Surface Testing:
- Dispatch 2-3 high-priority surfaces per round (avoid spreading thin)
- Instruct test agents to perform **deep, exhaustive testing**:
  - Multiple attack techniques per vulnerability class
  - Edge case exploration and creative exploitation
  - Attack chaining and combined vectors
  - Boundary condition testing
- Do NOT move to medium/low priority until ALL high-priority surfaces are thoroughly tested

### Medium/Low-Priority Surface Testing:
- Only test after high-priority surfaces are exhausted
- Can use broader parallel dispatch for quicker coverage
- Focus on most likely vulnerabilities, not exhaustive testing

### Priority Assessment:
High priority indicators: authentication mechanisms, admin panels, APIs with data access, file uploads, SQL/NoSQL queries, authorization controls

- **Stay non-destructive**: Explore bugs deeply but always maintain safety - no data deletion, corruption, or service disruption

## Parallelization Strategy

**IMPORTANT: Use `dispatch_requests` to dispatch multiple subagents in a SINGLE tool call.**

When you have multiple independent tasks, dispatch them together in ONE call using `dispatch_requests`:
- All subagents in the array run **concurrently** (up to 3 at a time)
- Results are returned together once ALL complete
- This is **much faster** than making separate sequential dispatch calls

**PRIORITY CONSIDERATIONS:**
- For high-priority surfaces: Dispatch 2-3 at most to enable deep testing
- For medium/low-priority surfaces: Can dispatch more in parallel for coverage

| Scenario | Use `dispatch_requests` for parallel dispatch |
|----------|----------------------------------------------|
| Multiple untested forms | `[{{"subagent_type": "test", "objective": "...", "focus_area": "/form1"}}, {{"subagent_type": "test", ...}}]` |
| API + Web interfaces | `[{{"subagent_type": "recon", "objective": "API recon", "focus_area": "/api"}}, {{"subagent_type": "recon", "objective": "Web recon", "focus_area": "/"}}]` |
| Multiple auth endpoints | `[{{"subagent_type": "test", "objective": "Test login", ...}}, {{"subagent_type": "test", "objective": "Test register", ...}}]` |

**Use single dispatch (sequential) ONLY when:**
- There's only one task to do
- Tasks have dependencies (e.g., need to create account before authenticated testing)
- Deep exploration of a single finding

## Subagent Dispatch Patterns

### Single Dispatch (one subagent)
Use this only when you have exactly one task:
```
dispatch_subagents(
    subagent_type="recon",
    objective="Perform comprehensive reconnaissance of the target",
    focus_area=""
)
```

### Parallel Dispatch (PREFERRED for multiple independent tasks)
**Always use this when you have 2+ independent tasks. Put all requests in ONE tool call:**
```
dispatch_subagents(
    dispatch_requests=[
        {{"subagent_type": "test", "objective": "Test login for auth bypass", "focus_area": "/login"}},
        {{"subagent_type": "test", "objective": "Test register for injection", "focus_area": "/register"}},
        {{"subagent_type": "test", "objective": "Test search for XSS", "focus_area": "/search"}}
    ]
)
```

All three run concurrently, results are aggregated when complete.

### Mixed Types (recon + test in parallel)
You can mix subagent types in the same parallel dispatch:
```
dispatch_subagents(
    dispatch_requests=[
        {{"subagent_type": "recon", "objective": "Deep API reconnaissance", "focus_area": "/api/v2"}},
        {{"subagent_type": "test", "objective": "Test authentication bypass", "focus_area": "/login"}},
        {{"subagent_type": "test", "objective": "Test for IDOR on user endpoints", "focus_area": "/api/users"}}
    ]
)
```

### Sequential Testing (dependencies)
```
dispatch_subagents(
    subagent_type="test",

    focus_area="authentication"
)
```

### Follow-up Investigation
```
dispatch_subagents(
    subagent_type="recon",
    objective="Deep dive into API endpoints discovered during initial recon",
    focus_area="/api/"

```

## Persistence Strategy

### When no findings exist yet:
When all attack surfaces have been tested but **no findings exist**, dig deeper:

1. **Ensure authenticated testing**: If you haven't created an account yet, do so and test authenticated surfaces
2. **Identify most promising surfaces**: Look for authentication, file uploads, APIs, admin panels
3. **Re-test with different techniques**: Try alternative payloads, edge cases, bypass methods
4. **Combine attack vectors**: Test chained attacks (e.g., XSS + CSRF, IDOR + privilege escalation)
5. **Test business logic**: Look for race conditions, workflow bypasses, rate limit issues

Only finalize after at least one round of deeper testing on the 2-3 most promising surfaces.

### When findings exist:
When bugs have been discovered, **go deep before moving on**:

1. **Maximize impact discovery**: Test the full extent of what the bug allows (non-destructively)
2. **Chain vulnerabilities**: Can this bug be combined with others for greater impact?
3. **Find variants**: Look for similar vulnerabilities in related functionality
4. **Test edge cases**: Push the boundaries of the vulnerability (safely)
5. **Document thoroughly**: Capture all exploitation paths and potential impacts

**Do not consider a finding "complete" until you've exhausted all reasonable exploration avenues.**

## Completion Criteria

Finalize the analysis when:
- Major attack surfaces have been tested **in both unauthenticated and authenticated contexts**
- **At least one of the following is true:**
  - Findings have been discovered, **thoroughly explored to their full potential**, and validated
  - Deep re-testing of promising surfaces yielded no results
- Coverage is sufficient for the assessment scope
- Further testing would genuinely yield diminishing returns
- **IMPORTANT**: If findings exist, they must be fully explored before finalizing - don't rush to completion
